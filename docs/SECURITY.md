# Security & Threat Model

**Status:** MVP starter. **Do not expose this as a public production service without implementing the release blockers below.**

## Threats / trust boundaries

| Boundary | Risks | Current baseline | Required hardening |
|---|---|---|---|
| Browser → Hub | password guessing, CSRF, session theft | signed 8-hour HttpOnly SameSite=Strict cookie; Origin checks on POST/PATCH/DELETE, exact required Origin for AI mutations | rate limit, CSRF token, login lockout, security headers, TLS proxy |
| First agent enrollment | token interception / reuse | 256-bit random token, SHA256 hash, 10min TTL, atomic consume | visibility/audit, abuse throttling, approval UI |
| Agent WSS | impersonation, replay, exfiltration | 256-bit bearer secret hashed in DB; auth before upgrade; no token in URL | cert trust, key rotation/revocation, versioning, mTLS option |
| Agent diagnostics | remote command abuse | enumerated safe tools, local service allowlist, fixed executable, 5s timeout, output cap | per-agent capabilities, policy engine, security testing |
| Docker access | host takeover via docker.sock | disabled by default; no socket mount | only through minimum-scope API proxy after explicit approval |
| Config / logs | secrets / PII leaks | hashes only for config; limited logs; simple regex redaction | tested secret scanners, opt-in per data class, preview/consent |
| Hub/DB | direct SQL/credential theft | parameterized SQL, localhost ports by default | encryption at rest/backups, separate DB roles, patching |
| LLM provider | untrusted input, data disclosure, wrong actions | bounded JSON response, validated evidence IDs, no action tools | prompt-injection evaluation, budget caps, disclosure policy |
| Worker queue | stuck job / duplicate processing | one queue via SKIP LOCKED | leases, idempotency, retries and poison-message handling |

## Secrets and configuration

- Use `bun run password:hash -- "..."` to generate Argon2id admin password hash. Never store clear admin password in production `.env`.
- Use a strong `SESSION_SECRET` (>=32 random characters), rotate on compromise.
- Use environment files with restrictive modes and protect backups.
- Provider API keys are entered only through authenticated same-origin settings and stored as AES-256-GCM envelopes in PostgreSQL. Only Hub/Worker/importer read `AI_PROVIDER_ENCRYPTION_KEY`; Web receives neither master key nor DB credentials, saved keys, or ciphertext. No runtime provider-key environment fallback.
- Agent identity secret stored 0600 on host or in protected Docker volume; remote use HTTPS/WSS.
- Host lists/history remain behind the existing admin cookie; enrollment token creation retains the existing Origin check, one-use token and audit path. The live inspector performs no diagnostics, outbound probe, LLM call or remediation. Workload/endpoint unavailability never implicitly enables Docker or shell access.
- The shared Web workspace layout checks the existing authenticated `/api/auth/me` endpoint before mounting any protected view or starting its reads. Signed-out deep links show sign-in at the requested route without fetching its protected data. Session-check outages offer retry without treating an API failure as authentication; any 401 clears the protected surface and cached workspace summaries. Incident-read outages do not bypass authorization or block independently authorized host reads. No new auth endpoint, credential storage, or server-side authorization change is introduced.
- For local development only, `DISABLE_AUTH=true` (with `NODE_ENV !== "production"`) bypasses the Hub admin session cookie check so the dashboard opens without login, and hides the browser sign-out control. Hub refuses to start if `DISABLE_AUTH=true` is set when `NODE_ENV=production`. `ALLOWED_ORIGIN` checks on mutating requests and agent enrollment/WSS authentication remain enforced.
- Network history derives aggregate rate estimates locally from existing authenticated host telemetry; no new collection or polling is introduced. Missing, ambiguous, reset and stale intervals are not presented as current traffic.
- The host dashboard's 60-second telemetry freshness label is a display policy, not a transport heartbeat or replay defense. `Online` means a socket is currently registered in this single Hub; silent network partitions still require transport TTL hardening. Enrollment tokens must not enter persistent browser storage, URLs, screenshots or logs; the admin-only enrollment view clears them on sign-out/expiry.
- Provider settings accepts one key per connection in a password input, never retrieves/reveals a stored key, and clears drafts on save/cancel/unmount/sign-out/unauthorized. No credential-derived masks or browser persistence. Save does not call a model; tests and investigations require explicit admin actions.
- The signed-in command palette filters existing host and incident summaries in browser memory. Queries and recent selections are not sent to the Hub, added to URLs, or persisted in browser storage. Palette options open existing views; enrollment token generation, diagnostics and provider calls still require their separate explicit actions.
- The opt-in `db:seed:demo` command is restricted to non-production, loopback database connections and uses a transaction with reserved fixture identities; it does not delete or overwrite existing rows. All hostnames, evidence, authored AI examples and resolution examples identify `Demo data`. Agent credentials are randomly generated and discarded, hosts remain offline, and investigation fixtures are completed/failed rather than runnable queue entries. Seeding starts no diagnostics, probes or provider calls; it must not be treated as collected evidence or a real confirmed resolution.
- An agent with Docker group membership often has root-equivalent power; never assume `docker.sock:ro` is safe just because the mount says `ro`.

### Curl onboarding trust and secret handling

The installation metadata API is admin-only. The Hub validates explicit deployment settings and never infers them from the browser, internal addresses, headers or query parameters. The public `GET /api/agents/install.sh` embeds only the non-secret HTTPS Hub origin, pinned release tag and repository as literal shell values in the packaged script. It returns 503 without valid HTTPS settings (including in loopback-only mode), serves successful responses with `no-store`, `nosniff` and shell-script content type, and returns 405 for other methods. The route does not proxy release assets or add unauthenticated enrollment authority; monitoring and manual enrollment remain available when configuration is missing or invalid.

The install command exposes its 10-minute, one-use token to shell history, clipboard and process arguments. Opening `/connect` does not issue a token; entering the install step or explicitly regenerating the command does. The wizard keeps the command only in memory and clears it on hide, expiry, leaving the install step, or leaving the wizard. This does not revoke the token or erase external copies; generating another does not revoke earlier tokens. Clipboard denial leaves selectable text. The waiting indicator uses fleet observations, not a token-to-host lookup. Verification still requires explicit host selection. Tokens must never enter URLs, persistent browser storage, env/unit files, logs or screenshots.

The HTTPS bootstrap ignores `.curlrc` and allows only HTTPS for the initial download and redirects: `curl -q -fsSL --proto '=https' --connect-timeout 10 -m 120 '<hubUrl>/api/agents/install.sh' | bash -s -- --token '<token>'`. The installer wraps its executable body in `main() { … }` and invokes `main "$@"` only as the final line, so a partial or truncated transfer ends in a Bash syntax error and executes nothing. The installer validates the token before requesting sudo. A nonroot piped run has no readable `$0`, so it serializes the configured installer into a private mode-0600 temporary script beside the mode-0600 token handoff file and re-executes that file only if sudo grants root; both files are removed on exit, HUP, INT and TERM. The token never appears in sudo's command line or standard input, and there is still no `curl | sudo bash`. A host that audits all process arguments can still record the token from Bash itself.

The installer downloads only pinned GitHub release assets over HTTPS with bounded timeouts, checks one exact archive checksum and rejects unsafe/extra archive members before mutation. Unsigned `SHA256SUMS` establishes archive integrity under the same HTTPS/GitHub trust, **not independent publisher authentication**. Public script delivery is also part of the trusted Hub/TLS deployment. No `latest`, arbitrary download-host override, tracing, eval or curl-to-root pipe is used.

Enrollment runs as the dedicated nonroot account and atomically saves a 0600 identity in its 0700 state directory. The finite command requires an HTTPS origin, refuses enrollment redirects and does not print response bodies/secrets. Valid identities are reused without token consumption; corrupt identities are preserved and rejected. No-argument monitoring retains HTTP only for local development compatibility. Tokens stay transient and are absent from the installed env and unit.
The unit explicitly sets `StateDirectoryMode=0700`; relying only on installer chmod is insufficient because systemd otherwise resets `StateDirectory` to its default 0755 at startup.

Same-version reruns require byte-identical binary/unit/env; conflicting files and symlink targets are refused, not overwritten. No upgrades, identity deletion or privilege-group grants are performed. A lost accepted enrollment response requires a fresh token, not invented recovery. Local service-active does not prove WSS connectivity or fresh telemetry. Pin a reviewed compatible release; an old binary without `enroll` is not compatible.

The separate foreground development mode explicitly opts into plaintext HTTP enrollment and WS only on `127.0.0.1`, with exact `NODE_ENV=development` and a literal configured origin matching the Hub's loopback listener port. The worktree runner refuses a non-loopback Web proxy bind in this mode. Do not expose either service through another proxy or port forward; same-machine processes can still reach loopback. Admin session, one-use token and agent checks are unchanged.

The development command runs `infra/install/agent-dev.sh` from the trusted local checkout root, not a script fetched from the Hub. The helper refuses root, disables `.curlrc` and proxies, requires certificate-checked HTTPS for the pinned GitHub downloads and redirects, and verifies exactly one matching SHA-256 entry before streaming only the binary into a private regular file. It does not extract into system directories or inherit production agent credentials/settings. Its identity and downloads are temporary; normal exit removes them. The release manifest is unsigned, so verification has the same integrity limitation as HTTPS installation.

## AI connection credentials and egress

Generate the master with `openssl rand -base64 32`; canonical base64 must decode to exactly 32 bytes. Back it up separately from PostgreSQL and share the same value only with Hub/Worker. Missing/malformed configuration leaves monitoring available; wrong key/tampered envelope fails `credential_unavailable`. There is no automatic master rotation or credential deletion/recovery. Restore the original master, or replace each provider key under a new master.

Each encryption uses a random 12-byte nonce, 16-byte tag and AAD `opspilot:ai-provider:v1:<uuid>`; storage is `v1.<nonce-base64url>.<ciphertext-base64url>.<tag-base64url>`. UUID is created before encryption. Endpoint/protocol changes require a newly entered key so an existing credential cannot silently move to another destination.

Worker transport uses native HTTPS with public-address classification and DNS pinning, original Host/SNI/certificate verification, `agent:false`, no proxy/global agent, no redirects or retries. It resolves every A/AAAA answer and rejects the entire target if any is nonpublic. IPv4 special-purpose ranges are blocked; IPv6 allows only 2000::/3 minus the documented special-purpose exclusions. This deliberately conservative policy may reject globally reachable special addresses. Private gateways, loopback, metadata and localhost are unsupported, without an override flag.

Every final operation URL is validated: HTTPS only, valid port, no userinfo/query/fragment/zone identifier. Total deadline is 30 seconds including DNS/body; TCP/TLS deadline 5 seconds, headers at most 16 KiB, body at most 1 MiB, identity encoding only. Late DNS cannot open a socket. `NODE_TLS_REJECT_UNAUTHORIZED=0` or active `BUN_CONFIG_VERBOSE_FETCH=1/curl` is rejected before requests. TLS verification cannot be disabled through the provider API.

Provider failures expose/persist/log only fixed categories and optional HTTP status, never upstream body, Location, raw URL/exception, auth headers or request body. Mutation/test-result audits are transactional and allowlist only protocol, revision, changedFields, testId, httpStatus, errorCode. Each provider retains one test slot, not unbounded test history. Credential deletion leaves non-secret investigation snapshots and audit events intact; general report/audit retention remains operator-managed.

Browser revision, queue snapshot and Worker claim checks prevent sending evidence to a configuration changed before execution. Once Worker captures configuration, an in-flight HTTPS request is not cancellable by edit/delete. A synthetic connection test can incur charges and validates generation/schema, not endpoint uptime or diagnosis quality. No model discovery, OAuth, fallback, automatic scheduling or remote execution is added.

Address policy references: [IANA IPv4](https://www.iana.org/assignments/iana-ipv4-special-registry/) and [IANA IPv6](https://www.iana.org/assignments/iana-ipv6-special-registry/). Enforce independent network egress controls as defense in depth.

### Provider usage, cost tracking and prompt-injection hardening

- Every completed investigation records the provider-reported token usage (`input_tokens`, `output_tokens`, `thinking_tokens`, `total_tokens`) and an optional `estimated_cost_usd` on the `investigations` row (migration `011_investigation_usage_cost.sql`), plus a transactional `ai.investigation.completed` audit event containing only non-secret metadata (incident/provider IDs, model, token counts, cost estimate). The estimate comes from a small static per-1M-token reference catalog for known models; unknown/custom models or missing token counts store `NULL` — costs are never fabricated. This is observability only: no hard budget block is enforced yet.
- Outbound prompts delimit all untrusted data (evidence, logs, prior incident memory) between explicit `BEGIN/END UNTRUSTED INPUT` markers and state that the content is data, not instructions; the system message repeats that evidence is untrusted. Log strings therefore cannot impersonate system instructions.
- Redaction before any LLM call now also covers GitHub tokens (`gh[pousr]_…`, `github_pat_…`), PEM private-key blocks, Basic/Digest auth headers, standalone `sk-…` keys, AWS `AKIA`/`ASIA` keys, Slack `xox…` tokens, JWTs and URL userinfo (`scheme://user:pass@host`) in addition to the original Bearer/`password`/`api_key`/`token`/`secret` patterns. Parser output is redacted again, so echoed secrets never reach stored results. Redaction remains regex-based first-line defense, not a complete secret scanner (see release blockers).
- Server-side post-processing strips every `evidence_id` not minted by the database and forces `confidence: "low"` when no valid citations remain, so hallucinated or injected citations cannot survive. Negative fixtures live in `tests/prompt-injection.test.ts` and `tests/provider-cost.test.ts`.

## Change events and incident timeline links

- Change events (`POST /api/changes`) and incident change links (`POST/DELETE /api/incidents/:id/changes...`, `GET /api/incidents/:id/timeline`) sit behind the admin cookie; mutations require the exact `ALLOWED_ORIGIN` and are audited (`change.recorded`, `incident.change_linked`, `incident.change_dismissed`, `incident.change_unlinked`) with non-secret metadata only (IDs, kind, service name, version, link status) — never title/summary/note text.
- Operator-supplied `title`, `summary` and link `note` are passed through the same regex `redact()` used for LLM payloads before storage, so accidental tokens/secrets in deploy notes are stripped; evidence previews in the timeline are redacted again and capped at 240 chars.
- Host isolation: timeline reads and link targets are scoped to the incident's `agent_id`; linking a change or config snapshot from another host is rejected with `409 cross_host`, and the timeline builder drops foreign-host rows defensively.
- Non-causal invariant: every change/config entry in API payloads and the UI carries `causation_claimed: false`, `relation` (`observed_nearby`/`operator_linked`), a relative `offset_seconds`, and the fixed notice that correlation does not establish root cause. Dismissal only hides nearby noise; it never asserts cause either way.
- All string lengths, query limits and time windows on the new routes are bounded (title 3-160, summary 1-1000, note 1-300, `occurredAt` at most 5m future / 365d past, list limit ≤100, window 5-1440m before / 0-720m after, per-query row caps).

### Incident-memory embeddings (opt-in hybrid retrieval)

- Hybrid memory retrieval (migration `014`) always runs bounded PostgreSQL FTS; the vector leg only activates when an operator explicitly enables it with `OPSPILOT_MEMORY_EMBEDDINGS_ENABLED=true`, a server master key exists, an enabled `openai-compatible`/`gemini` provider is configured, and the individual memory row carries `embedding_consent = TRUE` (opt-in per human-confirmed resolution). No paid external embedding API is ever called silently; without consent/config the system is FTS-only.
- Only curated human-confirmed `summary + resolution` is embedded — never raw logs or unredacted evidence. The text is passed through `redact()` and length-bounded (max 2000 chars) before any outbound request, and goes only through the DNS-pinned public HTTPS egress client (`postProviderJson`): SSRF/IP-blocklist/DNS-rebinding rules, 30 s total deadline and 1 MiB response cap apply unchanged. Provider vector responses are validated (finite numbers, 1–4096 dimensions, non-empty, non-zero norm) and L2-normalized before storage.
- `anthropic` connections are rejected with a typed `embedding_unsupported` error before any network request: Anthropic reasoning models do not imply an Anthropic embedding service, so Anthropic-only deployments remain FTS-only.
- The normalized vector is persisted in `embedding_values DOUBLE PRECISION[]` together with provenance (`embedding_model`, `embedding_provider_id`, `embedded_at`, `embedding_dimensions`, `embedding_consent`). When the server ships pgvector, a native `embedding_vector vector` column is added and used for `<=>` queries; plain `postgres:16-alpine` works via the exact in-app cosine fallback. Provider deletion nulls `embedding_provider_id` (`ON DELETE SET NULL`).
- The Worker embeds at most 5 canonical (`canonical_memory_id IS NULL`), consented, not-yet-embedded rows per tick; embedding failures never block or fail investigations. Recall@k is benchmarked before enabling (`tests/memory-retrieval.eval.test.ts`): on the repeat-incident corpus, hybrid RRF Recall@5 = 1.0 / MRR = 1.0 vs FTS-only 0.375, with zero false top-1 on distractor queries.
- Embedding requests are billable external calls like generation: each embedded row should be reviewed for retention policy of the chosen provider, and redaction is regex first-line defense, not a complete secret scanner.

### Incident memory deduplication, provenance and attribution

- Incident memory text (title/summary and resolution) is redacted with the shared `redact()` before it is fingerprinted, stored, or matched, so credentials echoed into a resolution never reach `incident_memory`, `incident_memory_sources`, fingerprints, or audit events (migration `015_memory_dedup_provenance.sql`).
- Deduplication never silently drops provenance: every contributing incident stays in `incident_memory_sources` (`PRIMARY KEY (memory_id, incident_id)`), and `POST /api/memory/merge` moves all source rows to the surviving canonical memory (`ON CONFLICT DO NOTHING`) before marking the source non-canonical; `occurrence_count`/`last_confirmed_at` are recomputed from distinct sources. Merged rows remain queryable via `canonical_memory_id`.
- `POST /api/incidents/:id/resolve` and `POST /api/memory/merge` sit behind the admin cookie and the `ALLOWED_ORIGIN` check (`401` unauthenticated, `403 forbidden_origin` on cross-origin), and write non-secret audit events only: `memory.created`, `memory.deduplicated`, `memory.merged` carry memory/incident IDs and occurrence counts, never text. `parseMergeMemoryRequest` strictly validates both UUIDs, rejects unknown keys and self-merges (`400`); unknown IDs are `404`, non-canonical operands `409`.
- FTS, vector and hybrid retrieval (`searchIncidentMemories`, `GET /api/memory`) and the Worker's prior-memory lookup only ever query canonical rows (`canonical_memory_id IS NULL`), so merged duplicates are never returned or embedded; they remain reachable through the canonical memory's `sources[]` provenance. The Worker additionally deduplicates exact/near-duplicate candidates before the LLM call and persists a bounded, non-secret `retrieved_memories_json` snapshot (memory ID, redacted summary, 200-char resolution preview, occurrence count, source incident IDs, retrieval method, score, last-confirmed timestamp) on the investigation row; `GET /api/incidents/:id` exposes it as `retrieved_memories`. The UI labels this as fallible prior context, distinct from measured signals, AI hypotheses, and the human-confirmed resolution of the current incident.
- Unit and integration coverage: `tests/memory-dedup.test.ts` (normalization, fingerprint, similarity, candidate dedup, strict merge parsing incl. self-merge/bad UUID/extra keys) and `tests/memory-dedup.integration.test.ts` (resolve-time dedup with multi-incident provenance, merge auth `401`/origin `403`/validation `400`/self-merge/`404`/`409`, `memory.merged` audit, worker attribution persistence and API exposure).

## Agent tool policy

Tools are fixed in source code:

1. `disk_usage` → `df -h` on agent-configured path.
2. `listening_ports` → `ss -lnt` (can expose internal service metadata).
3. `service_status` → `systemctl is-active <allowlisted service>`.
4. `recent_logs` → `journalctl -u <allowlisted service> -n 50`.
5. `docker_status` → `docker ps`, **agent flag required**, no docker socket mount in default Compose.

No arbitrary URL fetch, filesystem read, or shell script tool is permitted. Add filesystem restrictions before broad deployment.

### Periodic systemd status

The local operator opts in to one literal `.service` name. This collector does not share the diagnostic allowlist or accept Hub-supplied names, operations, arguments, environment or paths. The agent invokes `/usr/bin/systemctl --system --no-pager --no-ask-password show --property=LoadState,ActiveState -- <unit>` without a shell and with a minimal environment. One query per 15 seconds, bounded by a 3-second deadline plus pipe cleanup and 1 KiB stdout; stderr is discarded. No sudo, root privileges, extra groups, host socket mounts or service control is needed or added. Access denial, missing units, unrecognized output and timeouts are not mapped to stopped.

The Hub validates the version, complete object shape, single name, enum, size and clock window on the authenticated outbound socket. No client-supplied host ID is accepted. A superseded socket cannot submit new status, and older/equal observations cannot replace a newer one. The existing admin session gate protects selected-host reads. Only bounded unit/status metadata is persisted; raw command output and errors are never sent, stored or logged. The Hub retains the latest report and at most one last observed unit per host, not a history or per-sample audit stream. The periodic report is not a diagnostic action, liveness probe, remediation trigger or evidence about endpoint availability.

### Opt-in workload inventory

Two separate opt-in flags (`OPSPILOT_WORKLOADS_DOCKER`, `OPSPILOT_WORKLOADS_SYSTEMD`, both default false) enable periodic read-only inventory frames on the existing authenticated socket (connection + every 60 s). No Hub message configures, triggers or parameterizes collection; there is no generic shell or URL-fetch tool, and the frames are never derived from `docker_status` diagnostic output. Collectors run only fixed commands without a shell and a minimal environment: `docker ps --all --format …` plus best-effort `docker stats --no-stream --format …`, and `systemctl --system list-units --type=service --all --no-legend --plain`. Each command has a 5 s deadline, 32 KiB stdout / 4 KiB stderr cap, at most 64 entries per report and a 16 KiB frame budget (trailing entries are dropped if needed). Names are validated locally (docker container names 1–128 chars; literal `.service` units) and unparseable lines are skipped, never executed. States map only known values; timeouts, denials, missing binaries/daemon/manager are reported as `unsupported`/`unavailable` with a fixed reason enum, never as `stopped`. Docker access stays disabled by default, requires deliberate opt-in, and never mounts `docker.sock`; docker-group membership is root-equivalent. No sudo, root, extra groups or service control is needed or added.

The Hub validates frame size (16 KiB), exact v1 shape and key set, enums, name syntax per runtime, entry count, duplicate `(runtime,name)`, resource bounds, clock window and current-socket identity on the authenticated WSS, admitting at most one in-flight write per host; older/equal observations cannot replace newer ones. Only bounded metadata (name, runtime, state, optional CPU/memory) is persisted in `host_services` rows with `source='agent_workloads'`, plus one latest `host_workload_reports` row per host; raw command output and errors are never sent, stored or logged. Non-ok reports remove persisted rows so a failure is never shown as a measured empty fleet; freshness requires the current socket and a 120 s window. The existing admin session gate protects the read routes; workload state is not endpoint availability.

### Controlled config snapshots, semantic diffs and redaction

Config drift observability never becomes a generic file-read primitive. The agent reads **only** absolute paths already present in its local `OPSPILOT_CONFIG_FILES` allowlist (max 20), and only when the operator sets `OPSPILOT_CONFIG_DIFFS=true` (default `false`); the `config_diffs` capability is advertised only then, and the Hub negotiates it like any other capability. The Hub never sends file paths, never executes shell to read files, and no new tool exists. Before reading, the agent requires `os.Lstat` to report a regular file (symlinks, directories, devices and FIFOs are rejected and never followed), rejects files >64 KiB for diff reading (`too_large`; hash-only tracking up to 1 MiB is unchanged), and rejects binary content (NUL bytes or invalid UTF-8) as `binary_or_unreadable` — raw binary is never transmitted.

Secrets are redacted **on the agent before anything leaves over WSS**: Bearer/Basic/Digest authorization tokens; `password`/`passwd`/`pwd`/`api_key`/`token`/`secret` assignments; `*_PASSWORD`/`*_SECRET`/`*_KEY`/`*_TOKEN` env/INI keys; AWS `AKIA`/`ASIA` keys; GitHub `gh[pousr]_`/`github_pat_` tokens; PEM private key blocks; Slack `xox*` tokens; `sk-` API keys; JWTs; and URL userinfo (`scheme://user:pass@host`). Redacted content is truncated cleanly at 16 KiB per file, the whole `config_snapshot` frame is capped at 32 KiB (`MAX_CONFIG_SNAPSHOT_BYTES`, below the 64 KiB WS limit), and `redactionCount`/`truncated` are reported.

The Hub applies defense in depth: strict `parseConfigSnapshot` validation (exact key sets, absolute path syntax, SHA-256 format, canonical bounded timestamp, size caps, non-negative bounded counts, active-socket identity), then re-runs `redact()` on all received content before storing or diffing — agent redaction is never trusted alone. Only redacted content and bounded redacted semantic diffs are persisted (`config_snapshots` migration 012); the `/api/drift` routes require the admin session and never expose unredacted content. Drift entries and incident evidence explicitly state that config changes are **correlated, not proven causal** — the system never claims a config change caused an incident.

## Implemented inventory and endpoint monitoring

The [Fleet & services dashboard](UI-UX.md#fleet-services-dashboard-contract-target) defines broader collection requirements. The single-unit systemd slice above does not enable the planned tools or network access. The prohibition on arbitrary URL-fetch/shell diagnostics remains unchanged: there is no generic URL-fetch diagnostic tool, and probes run only against stored, admin-configured monitor targets.

- **Workload inventory (implemented):** opt-in, enumerated read-only collector slice described above (Docker/systemd inventory frames, fixed commands, deadlines and output/item bounds, explicit unavailable reasons). Missing capability or denied permission is explicit unavailable data. Do not mount `docker.sock`, enable Docker access or grant journal/root privileges merely to populate a dashboard. The prohibition on arbitrary URL-fetch/shell diagnostics remains unchanged.
- **HTTP checks (implemented):** dedicated operator-configured monitors in `endpoint_monitors` (migration 008 adds `enabled` and `check_interval_seconds`), never model-selected targets. All routes sit behind the admin session guard; mutations additionally require an Origin exactly equal to `ALLOWED_ORIGIN`. `POST /api/endpoints`, `PATCH`/`DELETE /api/endpoints/:id` and `POST /api/endpoints/:id/check` write `endpoint.created` / `endpoint.updated` / `endpoint.deleted` / `endpoint.probe` audit events. No unauthenticated probe endpoint exists. Bounded scheduling runs in the existing Worker boundary (`apps/worker/src/endpoint-scheduler.ts`): at most 8 due monitors per tick, claimed with `FOR UPDATE SKIP LOCKED`, each probed outside any DB transaction and persisted as an `endpoint_monitor_runs` row.
- **SSRF/egress (implemented):** URL validation (`validateEndpointTargetUrl` in `packages/contracts`) allows only `http`/`https`, rejects credentials, fragments, bad ports and oversized URLs, and classifies IP literals in pure TS: IPv4 special-purpose ranges (this-host, private, CGNAT 100.64.0.0/10, loopback, link-local incl. cloud metadata 169.254.0.0/16, benchmarking, documentation, multicast, reserved) and IPv6 outside global unicast 2000::/3 minus Teredo/documentation/6to4/ORCHIDv2/benchmarking subnets, with IPv4-mapped (`::ffff:`) and NAT64 (`64:ff9b::`) addresses unmapped to their embedded IPv4. `localhost`, `*.localhost` and metadata hostnames are rejected. At execution (`packages/ai/src/endpoint-probe.ts` + `egress.ts`) every DNS answer is resolved and validated with `node:net` BlockLists; if any answer is non-public the whole target is rejected, and the socket's `lookup` callback is pinned to one validated address while TLS keeps original Host/SNI/certificate verification — this prevents DNS rebinding. Loopback is reachable only through the explicit non-production `OPSPILOT_ALLOW_LOOPBACK_PROBES=true` mock; private homelab ranges have no client override. Redirects are followed manually at most 5 hops, re-applying the full URL and DNS/IP validation at every hop; a blocked hop yields `redirect_blocked`, exceeding the limit yields `redirect_limit`.
- **Execution bounds (implemented):** total deadline 5 s plus a 3 s connect deadline, header cap 16 KiB, response body read capped at 256 KiB and never stored, `agent: false` (no proxy/global agent), `rejectUnauthorized: true`, and `NODE_TLS_REJECT_UNAUTHORIZED=0` fails closed. Run history is bounded to 200 rows per monitor, pruned in the same transaction as each insert.
- **Sensitive targets/results (implemented):** audit events for monitor actions never include `target_url` or any URL fragment — only field names and non-secret values. Run rows store only status, HTTP status, latency, error code and timestamps, never response bodies or headers. Any later authenticated-check credentials must remain server-side and scoped to the configured destination; never forward browser admin cookies or provider keys. Hostnames, service metadata and HTTP errors remain untrusted data, not instructions.
- **Provenance and retention (implemented):** every run row records the actual named `probe_location` (server-side `OPSPILOT_PROBE_LOCATION`, default `hub-local`, never client-supplied) plus `started_at`/`finished_at` source timestamps; `GET /api/services` reports per-monitor `run_counts` scoped by `monitor_id` via LATERAL, never fleet-wide. `GET /api/endpoints/:id/runs` returns at most the newest 50 runs. No automatic LLM call, evidence upload or remediation occurs when a check fails or a user opens the inspector.

Negative tests in `tests/endpoint-security.test.ts` cover loopback/private/CGNAT/metadata IPs, encoded IPv4, IPv6 loopback/link-local/ULA/mapped/NAT64, redirect-to-private, excessive redirects, DNS-rebinding answers, timeouts, body cap, TLS-disable, unauthorized (401) and cross-origin (403) route access; `tests/endpoint-monitor.integration.test.ts` covers persisted runs, scoped counts, audit records and scheduler claiming against a real PostgreSQL. See [planned acceptance](TESTING.md#fleet-services-dashboard-acceptance-planned).

## Data retention

Metric telemetry is bounded by policy, not by disk luck: raw `metric_samples` are kept for `METRIC_RAW_RETENTION_HOURS` (default 168h), then rolled up per hour into `metric_samples_hourly` (count, min/max/avg, last network counters) and deleted in the same transaction by the Worker's `runMetricRetention`; rollups expire after `METRIC_ROLLUP_RETENTION_DAYS` (default 90d). Spent/expired enrollment tokens are deleted after 24h. Per-host alert thresholds and the alert condition state (breach streak, breached incident, cooldown) live in `alert_thresholds`/`alert_conditions` and survive Hub restarts; they cascade on host deletion. The agent-side queue is bounded on disk (`OPSPILOT_QUEUE_MAX_ENTRIES` default 2000 entries, `OPSPILOT_QUEUE_MAX_AGE_SECONDS` default 86400, 0600 file) so an unreachable Hub cannot grow it without limit; oldest samples are dropped first. Evidence, audit and investigation retention remain operator-managed per `docs/DATABASE.md`; retention exceptions for evidence tied to unresolved investigations are still planned. Deletion jobs are idempotent and audited where they touch configuration; raw metric deletion is not individually audited (volume), only the configured windows are.

## Minimum recommended network exposure

- Local development: bound Compose `3000`, `3001`, PostgreSQL `5433` to `127.0.0.1`.
- Remote production: expose only a hardened HTTPS reverse proxy (e.g. Caddy/Nginx) on 443. Proxy `/api/agents/connect` with WebSocket upgrade and long idle timeout.
- Do not publicly expose PostgreSQL or agent diagnostic interfaces.
- `COOKIE_SECURE=true` behind HTTPS; set correct `ALLOWED_ORIGIN` to public dashboard origin.

## Public design-system reference

The Next.js route `/design-system` is intentionally accessible without an admin session. It renders only authored synthetic examples and local React state: no host telemetry, incident records, credentials, provider keys, or database access. Preview validation, loading, and evidence disclosures do not call Hub APIs or save settings.

This route does not grant access to protected `/api` endpoints. Do not import server credentials or populate reference examples from live operational data. Dashboard and login UI checks using synthetic browser responses are not proof of authentication or authorization enforcement; the backend release blockers below remain unchanged.

The opt-in `dev:mock-dashboard` tool is separate from the Hub. It binds only to `127.0.0.1`, refuses `NODE_ENV=production`, and serves synthetic GET responses without authentication, credentials, database access, or outbound requests. Run the preview Web server on loopback too; never proxy the mock publicly or use it to test authentication, enrollment, probes, or provider calls.

The opt-in `dev:mock-agents` / `db:seed:mock` tool (`tools/mock-agents.ts`) refuses `NODE_ENV=production` and requires both `DATABASE_URL` and `MOCK_HUB_URL` to point to loopback hosts. ## CI trust boundary

`.github/workflows/checks.yml` (`CI — Tests & builds`) runs untrusted pull-request code only on GitHub-hosted runners using `pull_request`, not `pull_request_target`. It requests only `contents: read`, disables persisted checkout credentials, pins third-party actions to full commit SHAs, and bounds job duration. Keep production credentials and deployment steps out of validation.

Require the `TypeScript — Tests, types & Web build` and `Go agent — Tests` checks through a protected `main` branch rule without bypasses; migrate any old `typescript`/`go` required-check selections. Successful runs alone cannot prevent unchecked merges or direct pushes. SHA pinning prevents silent tag movement, not vulnerabilities in a pinned action or dependency.

## Release and package publishing

`release.yml` accepts version-tag pushes only, verifies strict SemVer and that the tag commit belongs to `origin/main`, and reruns CI before building/publishing. Protect `main` and restrict creation/update/deletion of `v*` tags to trusted maintainers using repository rulesets. An ancestry check is not a substitute for reviewed code or protected tags; repository rules must be configured separately.

The reusable `packages.yml` additionally requires a matching tag-push context. Only its image jobs receive `packages: write`; only the final release job receives `contents: write`. Publication uses the short-lived built-in `GITHUB_TOKEN`, never production credentials, enrollment secrets, database URLs or provider keys. OCI source/revision labels link images to the repository. `.dockerignore` excludes environment secrets, Git metadata and nested local dependency/build directories; do not pass secrets as build arguments or commit them into source.

Agent archives ship SHA-256 checksums, not signatures: these detect corruption but do not establish independent publisher authenticity. Signed releases, SBOMs, digest-pinned base images and security scanning remain roadmap work. Image pushes are not atomic across components or with GitHub Release creation; a failed run may already have updated image aliases. Use reviewed versions and record deployment digests rather than relying on mutable `latest`.

GHCR visibility/access is a separate package setting; new packages default to private. Review package Actions access and visibility after first publication. Public distribution must use a reviewed commit that includes the [MIT license](../LICENSE) and retain applicable third-party notices. Neither a stable tag nor successful publication resolves the production blockers below. No workflow deploys the application or enables network exposure.

## Privacy principle

Self-hosting Hub does not imply that data stays local after an LLM request. Clicking Investigate sends bounded selected incident evidence and retrieved resolution context to the explicitly selected connection endpoint/model. Review that destination and its retention/data-processing policy before sending non-synthetic data. Connection tests send only a synthetic prompt without incident evidence.
